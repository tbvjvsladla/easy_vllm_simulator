# hint 태그 발행 계약 (v2 · 2026-07-31 발효)

> 정본. `.claude/skills/upstream-version-watch/scripts/hint_tag.py` 가 이 문서의 규약을 집행한다.
> v1(암묵) → v2(명문) 전환이며, **v2 는 발효일 이후 생성 태그에만 적용**한다(§4 소급 금지).

## 1. hint 태그는 무엇인가

**이 프로젝트를 배포받은 다른 코드에이전트가 토큰을 아끼도록 "정답지의 일부를 살짝 보여주는" 자료다.**

- 목적은 **토큰 이코노미**다. 완제품 레시피가 아니라 **여정의 지도**다.
- 정보가 적은 태그는 **결함이 아니다** — 받는 에이전트가 나머지 여정을 스스로 밟을 뿐이다.
- 정보가 많은 신버전은 **참조할 데이터가 늘어난 것**이지, 구버전을 무효화하지 않는다.
- 따라서 **규약 버전 차이는 태그의 유효성과 무관하다.**

## 2. 진짜 위협 — 차단해야 할 단 하나

> **서빙이 실패했는데도 에이전트가 사용자를 속여 "서빙되었다"고 허위 기재한 정보가 배포되는 것.**

이것이 최대 위협이며, 게이트의 존재 이유다. 형식 미비는 위협이 아니다.
v1 게이트는 이 구분을 못 해서 **형식(footer 유무)으로 차단하고 증거(서빙 성공)는 검사하지 않았다.**
v2 는 차단 사유를 **형식 미비 → 증거 부재·위조**로 옮긴다.

## 3. 발행 가능 시점 (v2 필수 조건)

아래 **둘 다** 충족해야 발행 가능하다.

| # | 조건 | 근거 산출물 |
|---|---|---|
| A | **서빙전략 달성** — explorer 스킬로 레시피가 수렴하고 실제로 서빙됐다 | `docs/simlog/<run>/` 수렴 + `runtime.health_ok` + `functional_smoke_passed` |
| B | **정량지표 확보** — 벤치마커 스킬의 **lite** 지표가 실측으로 존재한다 | 인증서 `lite_included: true` + `lite_*` 열 |

- B 가 **lite** 기준인 이유: lite 는 서빙 성공 시 자동 수행되도록 설계된 **암시적 필수 계측**이다.
  full 은 선택이다. 다만 **full ⊇ lite 불변식**(§3.1) 때문에 full 을 돌렸다면 B 는 자동 충족된다.
- A 없이 B 는 성립할 수 없다(서빙이 안 되면 측정할 대상이 없다). 그래서 B 가 사실상
  **"서빙되었다"의 정량 증거**로 기능한다 — 이것이 §2 위협에 대한 실질 방어다.

### 3.1 full ⊇ lite 불변식

full 벤치는 lite 의 **상위집합**이어야 한다. 교집합이면 lite 로 잰 모델과 full 로 잰 모델의
지표 **열(column) 집합이 달라져 조건별 비교가 깨진다**.

구조적 보장: `sweep_bench.sh` 가 `lite_bench.sh` 를 **실제로 실행해서 포함**한다(병렬 목록 유지 ✗).
집행: `scripts/conformance_full_superset_lite.py`.

## 4. 레거시(v1) 태그 — 소급 적용 금지

v2 발효 이전 태그는 **재작성하지 않는다.**

- 그 태그들이 만들어질 당시엔 v2 증거를 요구하지 않았다 — **부재가 곧 허위는 아니다.**
- 이미 배포됐으므로 소급 차단해도 회수되지 않는다(차단의 실익 0).
- 태그 오브젝트 재작성은 원격 이력을 흔드는 되돌리기 어려운 작업이다.

**대신 SHA 로 핀한다**: 발효 시점의 레거시 태그를 각자의 태그오브젝트 SHA 로 등록한다.

| 상태 | 판정 |
|---|---|
| 핀 목록에 있고 SHA 그대로 | **경고**(v1 빈티지 · push 허용) |
| 핀에 없음 = v2 이후 신규 | **v2 조건 강제**(§3) |
| 핀에 있는데 SHA 가 바뀜 | **차단** — 레거시를 손댄 것이므로 v2 를 만족시켜야 한다 |

이 설계로 변조 탐지를 잃지 않으면서 레거시가 신규 발행을 막지 못하게 한다.

## 5. 차단 / 경고 분류

| 검사 | v1 | **v2** |
|---|---|---|
| 서빙 성공 증거 부재 | (미검사) | **차단** |
| lite 정량지표 부재 | (미검사) | **차단** |
| evidence-binding `forged` | 차단 | **차단** |
| evidence-binding `drifted` | 차단 | **차단** |
| evidence-binding `missing` (v1 빈티지) | 차단 | **경고** |
| 레시피 본문·tagger PII | 차단 | **차단** |

PII 는 배포 산출물이므로 `GENERIC_PII` 4종 전부가 그대로 강제된다(`.claude/rules/docs.md` §PII 스캔 적용 범위).

## 6. 발행 절차

```
match     근-미스 확인(read-only)
create    promotion-ready work-manifest + promotion_target 바인딩 → 스캐폴드
          ↓ TODO(judgment) 슬롯을 실측으로 채운다 (generic 문구 금지)
finalize  PII fail-closed 스캔 → annotated 태그 + 인덱스 갱신
verify    릴리즈 게이트(태그오브젝트·PII·인덱스 정합)
push      선별 배포 refs/tags/hint/*
```

`--tagger-name`/`--tagger-email` 은 **공개 신원**을 쓴다(운영자 신원은 PII 로 차단된다).
관례값: `easy-vllm-simulator <hints@easy-vllm.invalid>`.

## 7. 이 계약이 명문화된 이유

v1 은 **암묵 규약**이었고, 그 결과 게이트가 위협 모델과 어긋난 채로 굳었다 —
형식은 엄격히 막으면서 정작 "서빙되었다는 주장이 사실인가"는 아무도 검사하지 않았다.
2026-07-31 캠페인에서 신규 태그 1개가 레거시 23개의 형식 미비로 영구 차단되면서 드러났다.
