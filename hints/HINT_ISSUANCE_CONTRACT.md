# hint 태그 발행 계약 (v3 · 2026-09-01 개정)

> 정본. `.claude/skills/hint-publisher/scripts/hint_tag.py` 가 이 문서의 규약을 집행한다.
> v1(암묵) → v2(명문) 전환이며, **v2 는 발효일 이후 생성 태그에만 적용**한다(§4 소급 금지).

## 1. hint 태그는 무엇인가

**이 프로젝트를 배포받은 다른 코드에이전트가 토큰을 아끼도록 "정답지의 일부를 살짝 보여주는" 자료다.**

- 목적은 **토큰 이코노미**다. 완제품 레시피가 아니라 **여정의 지도**다.
- 정보가 적은 태그는 **결함이 아니다** — 받는 에이전트가 나머지 여정을 스스로 밟을 뿐이다.
- 정보가 많은 신버전은 **참조할 데이터가 늘어난 것**이지, 구버전을 무효화하지 않는다.
- 따라서 **규약 버전 차이는 태그의 유효성과 무관하다.**

## 2. 진짜 위협 — 차단해야 할 단 하나

> **서빙이 실패했는데도 에이전트가 사용자를 속여 "서빙되었다"고 허위 기재한 정보가 배포되는 것.**

이것이 최대 위협이며, 게이트의 존재 이유다. 형식 미비는 위협이 아니다.
v1 게이트는 이 구분을 못 해서 **형식(footer 유무)으로 차단하고 증거(서빙 성공)는 검사하지 않았다.**
v2 는 차단 사유를 **형식 미비 → 증거 부재·위조**로 옮긴다.

## 3. 발행 가능 시점 (v2 필수 조건)

아래 **둘 다** 충족해야 발행 가능하다.

| # | 조건 | 근거 산출물 |
|---|---|---|
| A | **서빙전략 달성** — explorer 스킬로 레시피가 수렴하고 실제로 서빙됐다 | `docs/simlog/<run>/` 수렴 + `runtime.health_ok` + `functional_smoke_passed` |
| B | **정량지표 확보** — 벤치마커 스킬의 **lite** 지표가 실측으로 존재한다 | 인증서 `lite_included: true` + `lite_*` 열 |

- B 가 **lite** 기준인 이유: lite 는 서빙 성공 시 자동 수행되도록 설계된 **암시적 필수 계측**이다.
  full 은 선택이다. 다만 **full ⊇ lite 불변식**(§3.1) 때문에 full 을 돌렸다면 B 는 자동 충족된다.
- A 없이 B 는 성립할 수 없다(서빙이 안 되면 측정할 대상이 없다). 그래서 B 가 사실상
  **"서빙되었다"의 정량 증거**로 기능한다 — 이것이 §2 위협에 대한 실질 방어다.

### 3.1 full ⊇ lite 불변식

full 벤치는 lite 의 **상위집합**이어야 한다. 교집합이면 lite 로 잰 모델과 full 로 잰 모델의
지표 **열(column) 집합이 달라져 조건별 비교가 깨진다**.

구조적 보장: `sweep_bench.sh` 가 `lite_bench.sh` 를 **실제로 실행해서 포함**한다(병렬 목록 유지 ✗).
집행: `scripts/conformance_full_superset_lite.py`.

## 3.2 성능 REFUTE — loop-until-done 과 사람의 중단권 (v2.1 추가)

통상 성능 REFUTE 는 **여기서 끝이 아니다**. 서빙전략을 재수립하고, 벤치마커의 측정 평면을
넓혀 가며(마지막 평면은 **사람이 수동 수집한 정보**까지 투입) **loop-until-done** 으로
반복해야 한다. 그 루프를 중간에 멈출 수 있는 것은 **사람의 지시뿐이다.**

사람이 그 지시를 내린 경우, hint 는 발행하되 **경고 플래그를 배포물에 박는다**:

> 서빙 성공은 했으나 성능이 기대 이하다. 이 자료를 서빙전략 수립에 쓸 때는
> **적대적 검증이 필요하다.**

### 집행 (fail-closed · 에이전트가 스스로 열 수 없다)

| 층 | 규칙 |
|---|---|
| work-manifest | `benchmark.perf_waiver` = `authorized_by` · `authorized_at_utc` · `instruction` · `warning_flag` **4필드 전부** 비어있지 않아야 유효 |
| `completion_gate.py` | waiver 유효 시에만 `verdict != PASS` 로도 승격 허용(`BENCHMARK_VERDICT_WAIVED`). 하나라도 비면 `BENCHMARK_PERF_WAIVER_MALFORMED` 로 차단 |
| `hint_tag.py finalize` | waiver 가 있으면 본문에 **`PERF-WARNING` 마커**와 **`warning_flag` 문구 원문**이 둘 다 있어야 한다. 없으면 차단 — 경고 없는 waiver 는 단순 게이트 우회다 |
| 인증서 | **여전히 PASS 때만 발행**한다(무변경). waiver 는 승격만 열 뿐 *"성능이 검증됐다"* 는 주장을 만들지 못한다 |
| lite 증거(§3 B) | REFUTE 경로엔 인증서가 없으므로 **항상 발행되는 bench_report** 에서 읽는다. 요구 강도를 낮추는 게 아니라 근거 문서가 다를 뿐이다 |

**설계 의도**: 이 예외는 에이전트가 추론으로 열 수 없는 **positive key** 다. 사람이 명시
선언해야 열리고, 열리는 순간 배포물에 경고가 강제된다 — 얻는 것(지도 배포)과 치르는 것(경고)이
같은 트랜잭션 안에 있다.

## 4. 레거시(v1) 태그 — **은퇴** (2026-09-01 · 대상 0)

> **이 절의 기구는 더 이상 작동하지 않는다.** v1 빈티지 태그 62건이 2026-09-01 전량 회수됐고
> (`plan_26090107` Phase 0b · 사용자 직접 실행), `hints/legacy_v1_pins.json` 과 `pin-legacy`
> 명령도 함께 제거됐다. **소급 대상이 0이므로 기구를 유지할 이유가 없다.**
> 태그 원본은 `seed/hint_tags_backup_26090108/`(62건 raw · 바이트 왕복 검증)에 보존된다.

**논거는 남긴다** — 같은 상황이 다시 오면 같은 판단을 하기 위해서다:

- 그 태그들이 만들어질 당시엔 v2 증거를 요구하지 않았다 — **부재가 곧 허위는 아니다.**
- 이미 배포됐으므로 소급 차단해도 회수되지 않는다(차단의 실익 0).
- 태그 오브젝트 재작성은 원격 이력을 흔드는 되돌리기 어려운 작업이다.
- 그래서 재작성 대신 **SHA 핀**으로 변조 탐지를 잃지 않으면서 레거시가 신규 발행을 막지
  못하게 했다. 이번에는 회수가 사람의 결정으로 이뤄져 핀이 불필요해졌을 뿐이다.

## 5. 차단 / 경고 분류

> **v3 단순화**: 분류기가 4등급(`blocking`·`legacy_warn`·`drift_warn`·`unverifiable`)에서
> **2등급**(`blocking`·`unverifiable`)으로 줄었다. 없어진 둘의 근거가 사라졌기 때문이다 —
> `legacy_warn` 은 빈티지 태그가 0건이 되어(§4), `drift_warn` 은 "등재된 드리프트는 통과"라는
> 경로 자체가 제거되어(감사 ⑯⑰: 그 분기는 존재하지 않는 계약 개정을 인용하고 있었다).

| 검사 | 판정 |
|---|---|
| 서빙 성공 증거 부재 | **차단** |
| lite 정량지표 부재 | **차단** |
| evidence-binding `forged`(위조) | **차단** |
| 레시피 본문·tagger PII | **차단** |
| **페이로드 트리 PII** (v3 신설) | **차단** |
| **슬롯 3신호 모순** (v3 신설) | **차단** |
| evidence 대조 불가(이 체크아웃에 증거가 없음) | `unverifiable` — 차단 아님 |

**등급은 메시지 문자열이 아니라 코드로 정한다.** v2 에서는 사람이 읽는 메시지의 substring 으로
등급을 매겨, 태그 저자가 통제하는 footer 값에 특정 문자열을 넣으면 **차단이 경고로 강등**됐다
(감사 ② 실측). 이제 판정은 `(code, message)` 튜플의 **code 로만** 한다.

PII 는 배포 산출물이므로 `GENERIC_PII` 4종 전부가 그대로 강제된다(`.claude/rules/docs.md`
§PII 스캔 적용 범위). **v3 부터는 태그 본문뿐 아니라 페이로드 트리 전량**이 대상이다 —
태그가 배포하는 것이 본문에서 트리로 바뀌었으므로 방어도 함께 이사했다(감사 N-3).

## 6. 발행 절차

```
match              근-미스 확인(read-only)
collect            3소스 수확 + 3항목 저작 스캐폴드 (기계는 사실만 · 판단 자리는 마커)
   ↓ 저작           마커를 채우고 slots.declaration.json 을 기입한다
check              저작 완료 + **슬롯 3신호 대사** fail-closed
publish(branch)    allowlist 트리 → 페이로드 PII → 앵커 3중 → hint 브랜치 커밋
seal               린터 L1–L5 + PII + evidence footer → annotated 태그(hint 커밋을 가리킨다)
verify             릴리즈 게이트(태그오브젝트·PII·카탈로그 정합)
push               선별 배포 refs/tags/hint/* (`--tags` 금지 — last-good-* 유출)
catalog derive     **원격 발행 태그**에서 index.json + HINTS.md 파생
```

**태그가 가리키는 것이 바뀌었다** — 코드 브랜치 커밋이 아니라 **hint 브랜치의 페이로드 커밋**이다.
그래서 archive 가 곧 재현 키트이고, 카탈로그의 진실원천은 로컬 상태가 아니라 **원격 발행 사실**이다.
손저작 색인 경로(`index`·`reindex`)는 폐쇄됐다 — 그것이 감사 ④⑤의 기전이었다.

`--tagger-name`/`--tagger-email` 은 **공개 신원**을 쓴다. v3 부터 **기본값이 공개 신원**이며
(`DEFAULT_TAGGER_*`), 실명을 쓰려면 명시해야 한다 — 이전 기본값(`git config`)은 잊으면 발행자
실명이 배포 태그에 박히는 구조였고 실제로 한 번 발생했다(push 전 회수).

## 7. 이 계약이 명문화된 이유

v1 은 **암묵 규약**이었고, 그 결과 게이트가 위협 모델과 어긋난 채로 굳었다 —
형식은 엄격히 막으면서 정작 "서빙되었다는 주장이 사실인가"는 아무도 검사하지 않았다.
2026-07-31 캠페인에서 신규 태그 1개가 레거시 23개의 형식 미비로 영구 차단되면서 드러났다.
