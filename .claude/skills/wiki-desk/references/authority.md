# 원문 권위와 검토·수용 경계

## 합의된 권위만 사용하기

문서 권위는 OKF 규격이 정하지 않는다. 대상의 실제 context·최신 사용자 지시·기존 합의와 원문을 확인하고 계약의 `authority_rules`/`fallback`을 사용한다. 예제 순서나 다른 프로젝트의 문서 계층을 강제하지 않는다.

`authority_rank`가 높은 후보를 먼저 읽는 것은 탐색 우선순위일 뿐이다. glob 일치·document type·rank·metadata의 `active`·내용 hash·문자열 연결만으로 의미상 승인이나 결과 수용을 판정하지 않는다. 현재 runtime은 순서 있는 규칙의 첫 일치를 적용한다. query 순위는 검색 점수가 1차이고 `authority_rank × search.authority_weight`가 가산·동점 처리에만 쓰인다(1.x의 rank 1차 정렬을 대체). 규칙이 겹치면 높은 rank가 앞 규칙을 자동 대체하지 않는다. 겹침이나 동순위가 중요한 판단에 영향을 주면 합의된 정책과 실제 원문을 대조한다. 해소되지 않은 충돌을 숨기지 않는다.

## 네 가지 서로 다른 판정

| 판정 | 필요한 근거 | 대체할 수 없는 것 |
|---|---|---|
| 위치/존재 | 실제 파일 또는 접근 가능한 artifact | descriptor, registry 검색 hit |
| 지식 신선도 | 현재 원문과 등록 내용·시점·범위의 대조 | 과거 확인, hash만의 의미 검토 |
| 지식 확인 | 실제 확인 actor·시점·범위·결과 | 자동 작성/색인, `generated` |
| 제품/작업 수용 | 현재 workflow의 승인 원문과 대상 결과·수용 범위 | `verified`, OKF `status`, 형식 PASS |

결과 수용·발행 허용·범위 한정·상담 검토·품질 보류·대기 상태는 다르다. 승인이라는 이름의 문서라도 실제 본문·대상·조건을 읽는다. 계획·의도·초안은 실행 결과가 아니다. 학술/외부 문서는 설계 근거가 될 수 있어도 프로젝트 실행 완료 증거는 아니다.

## 질의에 연결할 원문 계보

1. 현재 요청의 업무·시점·입력 범위를 명시한다. 같은 단어가 있는 다른 업무나 format sibling을 섞지 않는다.
2. 실제 정본 결과와 관련 지시·의도, 실행 증거, 실패/잔여, 후속 정정/수용을 선택해 읽는다.
3. 수용된 범위와 제외된 범위를 나눈다. 단일 교정·metadata 수리·형식 변환을 전체 제품 완료나 재평가로 확장하지 않는다.
4. 최신 후속 기록이 과거 pending을 해소했으면 그 계보를 설명한다. 반대로 과거 승인만으로 현재 상태를 승인됐다고 하지 않는다.
5. 답변에 판단·정확한 참조·실제 읽은 범위·남은 불확실성을 제시한다. 원문을 회수하지 못했으면 후보 수준의 안내라고 표시한다.

## ID·missing·stale·역사 보존

카드의 원문 경로(`resource`)와 `source_sha256`은 관측값이다. 경로가 이동했더라도 근거 있는 relocation 없이 새 ID로 갈아끼우지 않는다. 동일 ID 충돌·경로 재사용은 현재 파일의 연속성을 증명하지 않는다. 부재 source와 unresolved descriptor를 실제 파일로 위장하지 않는다.

런타임의 missing guard가 적용을 차단하면 원문 root·checkout·제외 범위·이동 계보를 확인한다. source를 무검토 삭제하거나 guard를 비활성화해 통과시키지 않는다. `stale` 또는 마지막 관측 이력은 현 상태 확인과 구별해 보존한다.

원문 history와 승인 문서의 결과를 바꾸지 않고 필요한 wiki delta만 갱신한다. 현재 요청 밖 제품 재실행·score 수정·별도 검토 발행을 자동 추가하지 않는다.

## 검토 후 등록

실제 결과 검토 → 대상 workflow에 맞는 사실 기반 검토/수용 기록 → 승인 범위의 wiki 등록 순서를 지킨다. 등록 작업은 인간 승인 위임장이 아니다. 확인 이력이 없으면 `verified`를 만들어 넣지 않는다. 결과 보고는 등록·원문 확인·의미상 수용·host 인식을 서로 다른 항목으로 유지한다.
