## 0. 핵심 고민(사용자)
- 분리 가능한 단일 기능: **메인노드 검증 결과물 → 서브노드 코드 업데이트(SSH/ConnectX-7)**.
- 전체 멀티노드 플로는 복잡: 코드검증 → 메인→서브 전달 → 양노드 동시기동 → 분산 LLM 서빙 확인.
- → 전달 기능만 잘라내고, 멀티노드 루틴은 **오케스트레이션 패턴 + 병렬**로.

## 1. CC 공식 아키텍처 (도출)
| 요소 | 결론 | 근거(공식문서) |
|---|---|---|
| 메인→서브 전달 | **스킬/스크립트** (MCP 아님 — SSH/rsync는 로컬 인프라). 고위험→`disable-model-invocation: true` + HITL | docs/mcp, docs/skills |
| 멀티노드 오케스트레이션 | 메인 대화=오케스트레이터. 순차=스킬, 독립·병렬=**서브에이전트(Task)** 동시 spawn → 메인이 종합 | docs/sub-agents, docs/agents |
| 병렬 실행 | background 서브에이전트 동시 실행(한 세션 내) | docs/sub-agents#run-in-foreground-or-background |
| HITL 게이트 | `disable-model-invocation`(고위험 스킬) + `AskUserQuestion` | docs/skills#control-who-invokes-a-skill |
| 알림/자동화 | `Stop`/`PostToolUse` 훅 | docs/hooks-guide |

- **인터뷰 결론과 정합**: "별도 스킬 아님(독립 트리거 없음)" = 캡슐화 단위 문제가 아니라 *독립 발동* 문제.
  전달은 **캡슐화된 스크립트/서브스킬**이되 멀티노드 오케스트레이션이 한 단계로 호출(독립 트리거 X). 모순 없음.

## 2. 권장 구조 (실env grounding 반영)
```
upstream-version-watch (멀티노드 path = 오케스트레이터)
├─ 순차: resolve → main 빌드 → single-smoke (Phase 1 검증됨)
├─ [전달] scripts/sync_to_sub.sh
│     rsync -az -e "ssh -o BatchMode=yes" --exclude __pycache__ --exclude .git --exclude seed/ \
│       <source> cona@192.168.100.11:~/ws_docker/vllm_serving_server/   (검증된 채널, HITL 게이트)
├─ [서브 원격 빌드] background 서브에이전트: ssh cona@192.168.100.11 'docker compose ... build' (교차검증, ~9GB 첫 pull)
├─ [2노드 동시 기동] master 로컬 + slave SSH 동시 → Ray 클러스터 병렬 형성(serve_runner.sh 5분 윈도우가 동시성 흡수)
├─ multi-smoke: master 엔드포인트(90XX) 추론 → 실패(OOM/NCCL/Ray)는 Model-C HITL
└─ push: 메인 전용(record/origin)
```

## 3. 실환경 사실 (grounding)
- 메인 `192.168.100.10`(spark-a73e) ↔ 서브 `192.168.100.11`(spark-bdc9), ConnectX-7 1.3ms, MTU 9000.
- passwordless SSH 복구됨(메인 id_ed25519.pub → 서브 authorized_keys). rsync 양측 보유, 채널 검증.
- 서브: aarch64/GB10/docker 29.2.1, multi-node 브랜치, NGC 캐시 0(첫 빌드 ~9GB). 메인과 동형 ws_docker.
