# vLLM 멀티노드 서빙 성능 문제 해결 개발로그

> **작성일**: 2026-04-22
> **대상 모델**: `gpt-oss-120b` (MXFP4 quantized, MoE 120B total / 5.1B active)
> **환경**: QSFP 케이블 1개로 직결 멀티도느, vLLM 0.19.1 + Ray
> **최종 성과**: Generation throughput **20 tok/s → 47 tok/s (2.35배)**, 안정적 재현

---

## 1. 문제 상황

### 1.1 초기 증상

메인 및 서브노드를 QSFP 케이블로 연결하고 `gpt-oss-120b`를 `tensor-parallel-size=2`로 분산 서빙했을 때, 싱글노드 대비 성능이 **오히려 저하**되는 현상 발생.

| 구성 | Prefill (tok/s) | Generation (tok/s) |
|---|---|---|
| 싱글노드 (TP=1) | 36 | 27 |
| 듀얼노드 (TP=2) | 32 | 26 |

일반적으로 TP=2는 선형에 가까운 성능 증가를 기대하나, **오히려 약간 감소**. 네트워크 통신이 병목이 되어 GPU 연산 이득을 상쇄한 것으로 추정.

### 1.2 커뮤니티 피드백

블로그 포스트에 다음 피드백 수신:

> "통신 노드 세팅이 잘못된 것 같다. 듀얼 구성에서는 선형에 가까운 성능 증가가 정상이며, 프리필 7000 중반 / 디코딩 70 중반 수준이 나와야 한다."

→ 물리 레이어 + 소프트웨어 레이어 모두 재검증 필요성 대두.

---

## 2. 진단 과정

### 2.1 [오진 1] 물리 레이어 의심

처음엔 "QSFP 케이블 1개만 연결되어 대역폭이 반토막"이라 가정. 그러나 NVIDIA 공식 포럼 조사 결과:

- 장치당 **200Gbps 상한이 하드웨어 고정**
- 케이블 1개로도 풀 대역폭(200Gbps) 확보 가능
- 오히려 **케이블 2개 사용 시 각 링크 100Gbps로 반토막**되는 구조

→ 오진 정정. 물리 레이어는 문제가 아님을 확인.

### 2.2 물리 레이어 실측 — `ib_write_bw`

양 노드 간 RDMA 대역폭 벤치마크로 하드웨어 상태 검증:

```bash
# 서버 측
ib_write_bw -d rocep1s0f1 -F

# 클라이언트 측
ib_write_bw -d rocep1s0f1 -F 192.168.100.11
```

**결과**:
- `rocep1s0f1` (Domain 0): **109.09 Gb/s**
- `roceP2p1s0f1` (Domain 2): **109.18 Gb/s**
- 합산 ~218 Gb/s로 **200Gbps 풀 대역폭 정상**

→ 물리 레이어와 RDMA 스택 자체는 완벽. **소프트웨어(NCCL) 레이어 의심**으로 전환.

### 2.3 NCCL 디버그 로그 분석

`NCCL_DEBUG=INFO`, `NCCL_DEBUG_SUBSYS="INIT,NET,GRAPH,ENV"` 설정 후 서빙 재기동.

**확인된 정상 동작**:
- HPC-X RDMA 플러그인 정상 로드: `/opt/hpcx/nccl_rdma_sharp_plugin/lib/libnccl-net.so`
- `NET/IBext_v11` 사용, RoCE v2 GID 3 사용
- 16개 채널 전부 `via NET/IBext_v11/0`로 라우팅 (TCP fallback 없음)

**결정적 이슈**:
```
NET/IBext_v11 : GPU Direct RDMA Disabled for HCA 0 'rocep1s0f1'
Connected all rings, use ring PXN 0 GDR 0
```

- **GDR(GPU Direct RDMA)이 비활성화**됨
- NCCL 토폴로지 분석 결과: GPU↔CPU는 C2C 345GB/s, CPU↔NIC은 PCI 12GB/s, NIC↔NET은 25GB/s
- GPU와 NIC가 **같은 PCI switch 아래에 없어**서 HPC-X 플러그인이 GDR을 거부

→ 데이터가 GPU→CPU→NIC→네트워크 경로로 우회 복사되어 오버헤드 발생.

### 2.4 Root Cause 요약

| 레이어 | 상태 | 문제 |
|---|---|---|
| 물리 (QSFP 케이블, 포트) | ✅ 정상 | — |
| RDMA 스택 (ib_write_bw) | ✅ 정상 (218 Gb/s) | — |
| NCCL 초기화 | ✅ 정상 | — |
| **NCCL 환경변수 설정** | ❌ **부적절** | GDR 비활성, HCA 매칭 모호, GID 미지정 |
| **GDR 경로** | ❌ **비활성** | C2C 경유 힌트 미제공 |

## 3. 해결 방법

### 3.1 핵심 가설

메인 및 서브노드는 `unified memory + C2C 345GB/s` 구조라, GPU-NIC이 동일 PCI switch에 없어도 **C2C 경유 GDR**을 활성화할 수 있다. NCCL 공식 문서의 `NCCL_NET_GDR_C2C` 옵션이 바로 이 케이스를 겨냥한 것.

### 3.2 적용한 환경변수 변경 (NVIDIA 공식 문서 기반)

| 변수 | Before | After | 이유 |
|---|---|---|---|
| `NCCL_IB_HCA` | `rocep1s0f1,roceP2p1s0f1` | `=rocep1s0f1` | `=` prefix로 정확 매칭 (prefix 매칭 방지, 공식 권장) |
| `NCCL_IB_GID_INDEX` | (미설정) | `3` | RoCE v2 명시 선택 (dynamic selection 회피) |
| `NCCL_NET_GDR_LEVEL` | (미설정) | `SYS` | 시스템 전체 GDR 허용 |
| `NCCL_NET_GDR_C2C` | (미설정) | `1` | C2C 경유 GDR 활성 |
| `NCCL_NET_GDR_READ` | (미설정) | `1` | GDR 읽기 허용 |
| `NCCL_CROSS_NIC` | (미설정) | `1` | 교차 NIC ring/tree 허용 |
| `NCCL_SOCKET_IFNAME` | `enp1s0f1np1,enP2p1s0f1np1` | `enp1s0f1np1` | Bootstrap 경로 단순화 |

### 3.3 docker-compose `x-gpu-common` 환경변수 최종안

```yaml
environment: &gpu-env
  # NCCL 디버그
  NCCL_DEBUG: "INFO"
  NCCL_DEBUG_SUBSYS: "INIT,NET,GRAPH,ENV"

  # RDMA 핵심
  NCCL_IB_DISABLE: "0"
  NCCL_IB_HCA: "=rocep1s0f1"          # '=' prefix로 정확 매칭
  NCCL_IB_GID_INDEX: "3"              # RoCE v2
  NCCL_IB_QPS_PER_CONNECTION: "4"
  NCCL_IB_SPLIT_DATA_ON_QPS: "0"

  # GDR
  NCCL_NET_GDR_LEVEL: "SYS"
  NCCL_NET_GDR_C2C: "1"               # C2C 경유 GDR
  NCCL_NET_GDR_READ: "1"

  # Cross-NIC
  NCCL_CROSS_NIC: "1"

  # Bootstrap 소켓 (단일 인터페이스)
  NCCL_SOCKET_IFNAME: "enp1s0f1np1"
  GLOO_SOCKET_IFNAME: "enp1s0f1np1"
  TP_SOCKET_IFNAME: "enp1s0f1np1"
  UCX_NET_DEVICES: "enp1s0f1np1"
  OMPI_MCA_btl_tcp_if_include: "enp1s0f1np1"
```

## 4. 해결 절차 (Step-by-step)

### Step 1. 네트워크 토폴로지 확인

```bash
# 각 노드에서 HCA 상태 확인
ibstat

# 예상 출력 (메인 노드)
# rocep1s0f0  — Down (미사용)
# rocep1s0f1  — Up (192.168.100.10)
# roceP2p1s0f0 — Down (미사용)
# roceP2p1s0f1 — Up (192.168.101.10)
```

Netplan 설정으로 양 도메인에 IP 할당되어 있는지 확인. netdev 이름의 **대소문자**(`enP2p1s0f1np1`의 대문자 `P`) 주의.

### Step 2. 물리 레이어 실측 (`ib_write_bw`)

```bash
# 서버 노드
ib_write_bw -d rocep1s0f1 -F --report_gbits

# 클라이언트 노드
ib_write_bw -d rocep1s0f1 -F --report_gbits 192.168.100.11
```

**합격 기준**: 100+ Gb/s 이상. 이보다 낮으면 물리 케이블/포트/netplan 설정을 먼저 해결해야 함.

### Step 3. docker-compose.yaml 환경변수 수정

`x-gpu-common.environment` 블록에 위 3.3 섹션의 NCCL 변수 전체 적용.

### Step 4. 서빙 재기동 및 로그 패턴 검증

```bash
docker compose --env-file envs/.env.gpt-oss-120b-MXFP4 --profile master up -d
docker compose logs -f vllm-master-serve | grep -E "NET/IB|GDR|ndevs|NET plugin"
```

**기대 로그 패턴**:
```
NCCL INFO NET/Plugin: Loaded net plugin NCCL RDMA Plugin v11 (v11)
NCCL INFO Successfully loaded external network plugin /opt/hpcx/nccl_rdma_sharp_plugin/lib/libnccl-net.so
NCCL INFO NET/IB : Made virtual device [0] name=rocep1s0f1 speed=200000 ndevs=1
NCCL INFO Using network IBext_v11
NCCL INFO Channel 00/0 : 0[0] -> 1[0] [receive] via NET/IBext_v11/0
```

**불합격 패턴** (있으면 트러블슈팅 필요):
- `NET/Socket` 경로 사용 → RDMA fallback 실패
- `TCP fallback` → HCA 설정 오류
- `Connection refused` → 방화벽 또는 IP 설정 오류

### Step 5. 성능 검증 (클라이언트 PC에서 반복 요청)

```bash
for i in {1..5}; do
  curl -sS http://192.168.0.19:9000/v1/chat/completions \
    -H "Content-Type: application/json" \
    -d '{"model":"gpt-oss-120b","messages":[{"role":"user","content":"Write a 500-word essay about space exploration"}]}' \
    > /dev/null
  sleep 2
done
```

서빙 로그에서 `Avg generation throughput` 값 추적. **합격 기준**: 싱글노드 baseline 대비 개선 + 표준편차 작음 (안정성).

## 5. 최종 결과

### 5.1 성능 지표

| 단계 | Prefill (tok/s) | Generation (tok/s) | 비고 |
|---|---|---|---|
| 싱글노드 (baseline) | 36 | 20 | TP=1 |
| 이전 멀티노드 (네트워크 미최적화) | 32 | 22 | 효과 없음 |
| **현재 멀티노드 (NCCL 최적화 후)** | **127** | **평균 47** (범위 39~54) | **2.35배 개선** |

### 5.2 안정성 검증 (5회 반복 테스트)

| 요청 # | Generation (tok/s) | 상태 |
|---|---|---|
| 1 | 31.8 → 53.7 | 200 OK |
| 2 | 42.7 | 200 OK |
| 3 | 49.1 → 46.4 | 200 OK |
| 4 | 43.9 → 51.3 | 200 OK |
| 5 | 45.2 → 50.6 | 200 OK |

- 5회 모두 200 OK
- 표준편차 작음 (안정적)
- Prefix cache hit rate 정상 누적 (4.7% → 22.2%)

### 5.3 듀얼 HCA 확장 실험 (참고)

`NCCL_IB_HCA="=rocep1s0f1,roceP2p1s0f1"`로 두 HCA aggregate 시도.

- **NCCL 로그**: `ndevs=1`로 aggregate 실패 (두 HCA가 서로 다른 PCI 루트)
- **성능**: 단일 HCA와 동일 (평균 ~46 tok/s)
- **결론**: gpt-oss-120b MoE (active 5.1B) 특성상 allreduce payload가 작아 200Gbps가 병목이 아님 → 듀얼 이득 없음. **단일 HCA 유지 권장**.

## 6. 배운 점

1. **"ib_write_bw 통과 ≠ NCCL RDMA 통과"**
   물리/RDMA 레이어가 정상이어도 NCCL 설정이 틀리면 GDR이 활성되지 않고 성능이 나오지 않음. 라이브러리 레벨의 별도 검증이 필수.

2. **NCCL_IB_HCA의 `=` prefix는 필수**
   prefix 없이 쓰면 NCCL이 prefix 매칭으로 처리해 경로 선택이 꼬임. NVIDIA 공식 문서에도 명시된 권장 사항.

3. **노드간 통신규격 : C2C는 GDR을 대체할 수 있다**
   GPU-NIC가 같은 PCI switch 아래 없어도, 345GB/s C2C 경유 GDR(`NCCL_NET_GDR_C2C=1`)로 성능 회복 가능.

4. **MoE 모델의 TP 이득은 Dense보다 작다**
   gpt-oss-120b는 active 5.1B라 allreduce 데이터가 적고, latency-bound에 가까움. 대역폭을 2배로 늘려도 이득이 크지 않음. Dense 70B 모델로는 다른 결과가 기대됨.

5. **NCCL 로그가 가장 강력한 진단 도구**
   `NCCL_DEBUG=INFO`로 토폴로지/GDR/경로가 모두 드러남. 문제 해결 시 반드시 활성화.

## 7. 미해결 과제 / 추후 과제

- **GDR 실제 활성 여부**: 로그상 `GDR 0`이 유지되나 C2C 경로로 성능은 회복됨. 실제 GDR 활성화 조건을 HPC-X 소스 레벨에서 확인 필요.
- **Dense 모델 교차 검증**: Llama-3.3-70B-NVFP4로 동일 테스트 시 "프리필 7000 / 디코딩 70"이 재현되는지 확인.
- **배치 throughput 측정**: `vllm bench serve`로 `--num-prompts 100 --request-rate 4` 시나리오 측정 → TP의 진짜 이득이 드러나는 지표.
- **Async scheduling**: Ray backend에서 비활성 상태. vLLM 구조적 한계로 현재 우회 방법 없음.
