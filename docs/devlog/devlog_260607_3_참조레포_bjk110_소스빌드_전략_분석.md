# devlog 260607-3 — 참조 레포 bjk110/spark_vllm_docker 소스빌드 전략 분석

## 배경
Step 3에서 prebuilt vLLM 0.22.1 wheel이 NGC torch 2.11 alpha와 C++ ABI 불일치로 서빙 불가임을 규명
(`testlog_260607_2`). 사용자가 참조해 온 레포 https://github.com/bjk110/spark_vllm_docker 가
같은 문제(DGX Spark + 최신 vLLM)를 어떻게 푸는지 조사함.

## 핵심: prebuilt wheel 아님 → NGC PyTorch 위 **소스 빌드**
- Base: **NGC PyTorch 26.04-py3** (torch 2.12.0a0, CUDA 13.2 native). ※ vLLM 0.21.0인데 베이스는 2.12 →
  소스 빌드는 torch 접두어 정확매칭보다 **API 패치로 브리징**하는 방식.
- vLLM: `git clone` → `git checkout ad7125a4`(v0.21.0) → 패치 적용 → `python3 setup.py bdist_wheel`.
  **`_C`/`_C_stable_libtorch`를 NGC torch에 맞춰 컴파일** → 우리가 막힌 C++ ABI 월(#5)이 원천 소거됨.
- 멀티스테이지: `flashinfer-builder` → `vllm-builder` → `runner`. 빌드는 Spark 노드 필요(C++/CUDA 컴파일 RAM).
- 빌드 가속: `MAX_JOBS`, `ccache 50G`. `TORCH_CUDA_ARCH=12.1a`(SM121/GB10).

## 우리 이슈 체인 ↔ bjk110 패치 (1:1)
| 우리 발견 | 그들의 해결 |
|---|---|
| #3 `register_opaque_type(hoist)` (NGC 26.03) | **`fix_pytorch211_compat.py`** — hoist kwarg 제거 (문서에 "NGC 26.03 environments" 명시) |
| #5 `_C.abi3.so` undefined symbol (CUDAStream::query) | **소스 빌드**로 `_C`를 NGC torch에 컴파일 → ABI 일치 |
| #4 libcudart / NCCL 경로 | `nvidia-nccl-cu13==2.30.4` + `LD_LIBRARY_PATH` 우선순위 (우리와 동일 기법) |
| torch 2.12 alpha API 드리프트 | **`patch_split_module_compat.py`** — `split_module(tuple_return=...)` 런타임 시그니처 검사 |

## 추가 패치 (참고)
- 빌드타임: `apply_sm121_fp8_pr35568.py`(PR #35568 cherry-pick, SM120→SM12x FP8 게이트 확장),
  `apply_sm121_patches.py`(is_blackwell_class, FlashInfer NVFP4, TRITON_PTXAS_PATH).
- 런타임: `fastsafetensors_natural_sort`(샤드 정렬), `aot_cache_fix`(NGC 26.03 pickling), `nogds_force`(GB10 GDS 부재),
  `moe_config_e256/e512`(GB10 MoE 튜닝), TurboQuant PR들(#40074/#39988/#39931).
- 의존성: `uv pip` system 모드(`PIP_BREAK_SYSTEM_PACKAGES=1`). 결과물 GHCR 배포(`ghcr.io/bjk110/vllm-spark`).

## 결론 / 우리 프로젝트에의 함의
1. **소스 빌드가 정답**임을 외부 사례가 확증. prebuilt는 torch 2.11 alpha 구간에서 불가(우리 testlog와 일치).
2. 우리 스킬은 **"prebuilt 스모크 실패 → 소스빌드 폴백 분기"**를 가져야 함. 폴백 빌드 골격(멀티스테이지 + 패치 디렉터리 +
   `fix_pytorch211_compat`류 + TORCH_CUDA_ARCH=12.1a + ccache)을 bjk110 구조에서 차용 가능.
3. 우리가 이미 만든 자산(`HAS_OPAQUE_TYPE=False` 패치, LD_LIBRARY_PATH, resolve 체인)은 소스빌드 경로에서도 재사용됨.
4. 빠른 시작 옵션: `docker pull ghcr.io/bjk110/vllm-spark:v022-d568` (그들의 사전 빌드 이미지) → 우리 compose/configs에 연결.
