검토일은 2026-10-30 KST, 현재 프로젝트 기준은 `multi-node`의 `d8a62994ad2ba2d880503d913661fd5a8d899734`다. 사용자 요청의 1·2단계에 해당하는 자료 분석과 방법론 제안이다. 실제 헌장 개정·코드 집행·행동 비교 실험은 3·4단계의 작업이다.

## 이미 합의되어 있는 프로젝트의 경계

현재 `CLAUDE.md`의 첫 불변식은 유효 결과와 절차를 재사용하고 변경·실패의 영향 범위만 확인하며 필수 검증과 정리 후 종료하도록 정한다. 따라서 종료 원칙 자체가 처음 필요한 상태는 아니다. [P1]

또한 `relay.py::reuse_completed_handoff`는 같은 context의 완료 리포트와 적용 범위를 확인하여, 새 인계 문제가 없는 재지시에서 worker를 다시 시작하지 않고 기존 결과를 반환한다. 실제 인계 문제를 명시한 feedback이나 바뀐 캠페인 입력은 별도 경로로 남는다. 이것은 **릴레이의 특정 공식 경로에 있는 가드**이며 모든 셸 명령과 모든 메인 세션의 추가 검증을 통제하는 전역 장치는 아니다. [P2]

2026-09-12 계획의 §3.8과 현행 `constitution_lint.py`는 고정 삭제 비율·정량 차단 임계·상시 절제 실험을 채택하지 않았다. 2026-09-30 계층화 계획도 이 INFO/WARN 계약을 유지한다. 이번 요청을 이유로 삭제율 목표나 매 작업의 비교 실험을 새 상시 의무로 만들 필요가 없다. [P3][P4]

보존할 다른 경계도 있다. 도메인 규칙의 권위는 공통 헌장·정책·manifest·캠페인에 있고 native 실행문법은 provider adapter가 소유한다. `*.topology.md`는 각 브랜치에 남는다. 정상 예산 소진 뒤 재개와 과업의 수명을 구분하며, 누적 워커 호출 횟수를 캠페인 종료 조건으로 삼지 않는다. 독립 검수가 필수인 hint 발행, 승인·정체성·호스트 안전·정리 의무도 간소화의 삭제 대상이 아니다. [P1]

## 간소화의 판단 단위

문장을 줄이기 전에 하나의 의무와 그 적용 조건을 식별한다. 같은 문장에 보호 규칙과 작업 요령이 섞여 있으면 먼저 분리한다. 이후 다음 분류를 적용한다.

| 분류 | 보존할 것 | 우선 처분 |
|---|---|---|
| 보호 규칙 | 권한·정체성·비밀정보·외부 효과·파괴적 작업·호스트 안전 경계 | 의미와 집행을 유지하고 중복 설명만 합침 |
| 업무 계약 | 목표·출력 형식·필수 검수·측정 출처·완료 판정·소유 | 짧은 선언과 실제 소유자·검사로 연결 |
| 행동 보정 | 과거 실수 뒤 덧붙인 반복 주의·추상적 철저함 요구·풀이 방식 강제 | 현행 필요성을 대조해 축약·삭제·보류 |
| 작업별 지식 | 특정 빌드 트랙·모델·실패·문서 종류에 필요한 상세 | 조건부 참조로 이관하고 도달 경로 유지 |

“모델이 충분히 좋아졌다”는 가정만으로 보호 규칙이나 업무 계약을 지우지 않는다. 확실한 중복은 최종 상태의 남는 소유자를 확인해 정리하고, 행동 변화가 불확실한 후보만 작은 비교 대상으로 둔다. 증거가 부족하면 후보를 보류할 수 있으며, 그 보류가 무제한 추가 검증으로 이어지지는 않는다.

후보 목록은 기존 계획 문서에 `현재 의무 / 역할 / 남는 소유자 / 읽을 조건 / 기존 집행·관측 / 처분`으로 기록하면 된다. 새 영구 원장이나 문장별 상시 승인 시스템을 만들 필요는 없다. 추적 파일의 원본과 복구는 git 이력·worktree를 사용하고 별도 백업 사본과 중복 digest를 만들지 않는다.

## 검증 범위와 종료의 작업별 계약

작업 시작 시 기존 계획이나 과업 기록에 다음을 정한다. 단순한 문서 수정까지 별도 YAML·스킬·캠페인을 만들라는 뜻은 아니다.

- 이번 산출물과 변경 범위, 결과를 받아들일 완료 기준.
- 각 기준을 확인할 필수 검사와 적용 조건, 사용할 수 있는 기존 근거.
- 어느 변경·실패·구체적 문제가 해당 근거를 무효화하는지와 처방 소유자.
- 기준 충족 뒤 남는 정리·요청된 발행·필수 커밋, 그 뒤의 결과 보고.

여기서 필수 검사와 추가 검사를 구분한다. 처음 계획한 필수 검사를 아직 실행하지 않았다면 미완료 작업이지 금지할 반복이 아니다. 선언된 benchmark 반복 측정이나 독립 hint 검수도 해당 업무의 필수 조건이므로 그대로 수행한다.

공통 헌장에 넣을 수 있는 짧은 대체 문안은 다음과 같다.

> 작업마다 완료 기준과 필요한 검증 범위를 정하고, 적용 조건이 유지되는 근거는 재사용한다. 필수 검증·정리·요청된 발행이 끝나면 결과를 보고한다. 추가 검증은 새 실패나 변경으로 기존 근거가 무효화되었거나, 완료 판정에 영향을 주는 구체적 미해결 문제가 있을 때 해당 범위에 한해 수행한다. 새 세션·하네스 전환·막연한 의심만으로 같은 검증을 반복하지 않는다.

이 문안은 현재 첫 불변식을 교체할 후보이며 별도 정책 단락을 덧붙이는 안이 아니다. 구체적인 예외 절차와 검사 명령은 헌장에 늘어놓지 않고 기존 workflow·owner 계약에 둔다. 반복 검증을 막는 규칙을 추가 검증 의무로 해석하지 않도록, 최종 완료 뒤의 기본 동작도 명시한다.

## 모델의 예외 판단을 줄이는 집행 방식

문구만으로 모든 도구 실행을 막을 수는 없다. 3단계에서 기존 검증 진입점·완료 판정·릴레이의 호출 경로를 대조하고, 실제로 연결할 수 있는 공식 경로에 한해 작은 판정 로직을 둬야 한다.

추가 검사 요청은 최소한 **완료 기준, 검사 대상, 직전 근거, 새 사건의 근거, 영향 범위**를 연결한다. 기록된 코드·입력 변화나 실패 결과처럼 기계가 확인할 수 있는 사실을 사용하며, “필요한 예외”라는 산문만으로 문을 열지 않는다. 구체적 문제의 의미·관련성은 담당자가 검토하고, 검사기는 자연어 전체의 진위를 판정한다고 주장하지 않는다.

| 관측된 상황 | 다음 행동 |
|---|---|
| 기준을 충족한 유효 근거가 있고 새 사건 없음 | 근거 재사용 후 정리·발행을 마치고 보고 |
| 필수 검사가 아직 충족되지 않음 | 미완료 필수 검사 수행 |
| 변경이 특정 근거의 적용 조건을 깨뜨림 | 관련 검사만 다시 수행 |
| 새 실패 또는 완료를 바꿀 구체적 문제 있음 | owner가 수정·설명한 뒤 해당 문제 확인 |
| 새 세션, 검증자 교체, 동일 검사 이름 변경, 일반적 불안만 있음 | 추가 실행 사유로 삼지 않음 |
| 사용자 요구가 바뀜 | 작업 범위·완료 기준을 개정하고 그 범위에서 계속 |
| 실제 권한 거부·정체성 불일치·미해결 실행·잔존 서비스 있음 | 기존 차단·복구·정리 계약 유지 |

현재 `completion_gate.py`는 업무 종류에 필요한 증거와 승격 상태를 판정하고, `harness_verify.py`는 정책·회귀 검사를 실행한다. 이들이 이미 모든 재검증 요청의 허용 여부를 판정하는 것은 아니다. `relay.py`의 완료 결과 재사용 가드도 정해진 인계 경로만 보호한다. 따라서 기존 writer와 상태를 재사용하되, 어떤 공식 호출자가 새 판정을 통과하는지 먼저 연결해야 한다. [P2][P6]

일반 셸 실행까지 통제하려면 별도의 도구 중재 범위가 필요하다. 그 경계를 구현·검증하지 않은 채 “Codex와 Claude의 모든 추가 검증을 코드로 차단한다”고 설명해서는 안 된다. 간소화의 1차 목표는 공통 업무 정책과 공식 실행 경로의 일치다.

## Planner Builder Validator 단계의 실행안

| 단계 | 수행 내용 | 종료 조건 |
|---|---|---|
| Planner | 보호할 의미, 편집 후보와 유일 소유자, 조건부 발견 경로, 관련 검사와 재진입 조건을 계획에 묶음 | 누락된 의무·소유자·관측 항목이 없고 실행 범위가 명확함 |
| Builder | 같은 의미의 작은 묶음으로 축약·이관하고 필요한 기존 호출 경로만 수정 | 최종 문서·코드 집합이 계획한 의무·경로를 보존하고 범위 밖 변경 없음 |
| Validator | 선언된 구조·호출 경로 검사와 필요한 의미 검토를 수행하고 검증 종료 동작을 확인 | 요구 기준 충족, 중대한 미해결 문제 없음, 정리·기록 후 결과 보고 |

검증자가 문제를 찾으면 그 문제와 관련된 Builder 수정·Validator 확인으로 잇는다. 관련 없는 전체 검사를 단계마다 처음부터 다시 돌리거나 검증자의 수를 늘려 합의할 때까지 반복하지 않는다. 소스 변경·새 실패가 없고 기준을 충족하면 완료를 보고한다.

3단계의 최소 검증 사례는 다음과 같다. 현재 실행한 테스트 목록은 아니다.

| 사례 | 확인할 결과 |
|---|---|
| 유효 근거가 있고 추가 사유 없음 | 새 검증 실행 없이 보고 단계로 진행 |
| 일부 필수 기준 미충족 | 완료로 오판하지 않고 그 검사 실행 |
| 특정 코드·설정·입력의 변경 | 무효화된 범위만 재검증 |
| 완료를 바꾸는 실제 문제 제기 | 근거와 owner를 통해 처리 경로 개방 |
| 같은 검사에 이름만 바꾼 재요청 | 별도 새 검증으로 세지 않음 |
| 문서 표현만 바꾸고 런타임 입력은 유지 | 문서의 변경 범위 확인, GPU·벤치 전체 재실행 없음 |
| 승격·승인·정체성·미해결 실행의 차단 | 검증 종료 규칙으로 우회하지 않음 |
| 두 문서가 서로 남겼다고 가정하며 같은 의무 삭제 | 최종 집합의 누락을 발견하고 복원 |
| 공통 참조 이관 | Claude와 Codex의 진입·발견·배달 경로가 모두 유지 |

기존 정책·문서 앵커·스킬 공개 표면·렌더 의존성이 바뀌면 그 범위의 기존 검사를 사용한다. 의미와 배달에 영향을 주지 않는 문서 정리만으로 전체 serving E2E나 성능 측정을 새로 열지 않는다. 실험용 scratch를 새 상시 의존성으로 편입하지 않는다.

## 모델과 지침의 상호작용을 구분하는 비교

먼저 같은 하네스·같은 모델에서 기존 헌장과 간소화한 헌장을 비교해야 한다. 입력 과업, 도구·권한, 모델 선택과 실제 실행 근거, effort 정책, 시작 상태를 고정하거나 차이를 명시한다. 모델 교체와 헌장 변경을 동시에 하면 개별 효과가 아니라 구성 전체의 비교다.

이후 여러 모델에서 같은 비교를 수행하면 지침 변경의 효과가 모델에 따라 달라지는지 관측할 수 있다. 동일 모델을 Claude와 Codex 양쪽에서 실제로 실행할 수 있을 때만 모델×하네스 교차 비교를 추가한다. 네 조합을 만들 수 없거나 실제 모델을 관측하지 못하면 모델 효과와 하네스 효과를 분리했다고 주장하지 않는다. 숫자가 같은 effort 이름도 모델·라우터마다 같은 추론량을 뜻하지 않으며 각 해소 경로를 기록한다.

평가 항목은 요구 충족·보호 경계·정당한 재검증 허용·완료 뒤 불필요한 검사 수·전체 시간과 토큰·실패 및 복구 비용이다. 프롬프트 바이트 감소만으로 효율 개선을 선언하지 않는다. 비용 비교를 하려면 실행 순서·반복 수·허용 차이·중단 조건을 결과 전에 정하되, 이 비교는 불확실한 후보의 한정된 실험이며 모든 작업의 상시 통과 절차가 아니다. 이전의 일반적 지침에서 호출 횟수 상한을 가져와 프로젝트 캠페인의 수명 제한으로 만들지도 않는다.

## 이번 단계의 결과와 다음 적용 범위

1·2단계의 결론은 **기존 보호·업무 계약을 유지하는 의미 단위 간소화와 작업별 검증 종료 정책을 함께 설계하는 것이 적합하다**는 것이다. 상시 문구를 추가하는 방식과 Claude 내부 패처 적용은 권장하지 않는다. 실제 효과와 공식 경로의 집행 범위는 3·4단계에서 확인할 대상이다.

이번 분석의 확인 범위는 세 로컬 자료와 대표 override 본문, 현행 공통 진입 문서, 기존 관련 결정, 릴레이·완료 판정·린트의 실제 코드다. `constitution_lint`의 정보 출력과 파일 계측을 보존했고 헌장 개정·모델 호출·전체 회귀·서브 배포·브랜치 동기화는 실행하지 않았다. 분석 보고서 발행을 단순화 정책이 이미 적용된 것으로 기록하지 않는다.

수용 기준이나 실제 도구 중재 범위를 바꾸어야 하는 모호성이 3단계에서 남으면 사용자 지정대로 Ouroboros 딥 인터뷰로 그 결정만 정리한다. 이번 자료 분석을 완료하기 위해 새 인터뷰나 과거 E2E의 재실행은 필요하지 않았다.
