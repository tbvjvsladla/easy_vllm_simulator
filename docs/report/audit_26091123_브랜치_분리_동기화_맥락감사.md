## 0. 요지

1. **두 브랜치의 빌딩블럭은 바이트 동일하다.** `git diff single-node multi-node -- .claude CLAUDE.md campaigns README.md`
   = 0. 갈라진 것은 23파일뿐이고 그 대부분이 산출물 핀·토폴로지 전용 configs·report·hint 카탈로그다(§2).
2. **헌법은 "브랜치로 토폴로지를 추론하지 않는다"고 말하지만, 코드 13곳이 브랜치 이름에서 토폴로지를 파생한다**(§3).
   그 파생이 `output/<topology>/manifest.yaml` 경로를 고르므로, "manifest 가 토폴로지 권위"라는 문장은
   실행 평면에서 "브랜치가 manifest 를 고른다"로 뒤집혀 있다. 이것이 분리가 무의미해진 기계적 뿌리다.
3. **동기화 스크립트의 자기 정의는 "정본(main) → multi-node 단방향 미러"인데 정본 브랜치 `main` 은 존재하지 않고**,
   실무는 환경변수로 방향을 바꿔 **양방향 99회**(s→m 40 · m→s 50 · 무표기 9)로 돌았다. 정본 자리는
   2026-08-24 를 경계로 multi-node → single-node 로 **뒤집혔다**(§4).
4. **브랜치 전환이 모드 선언이 아니라 체크아웃 토글로 쓰인다** — 최근 9일간 메인 워킹트리에서 single↔multi
   전환 74회(9-10 하루 20회). 서빙 중 전환 금지 함정(README §B-1)이 그 위에 얹혀 있다(§2.4).
5. 캠페인 이력에서 브랜치는 **한 번도 실행 통제변인으로 검증되지 않았다** — `campaign.yaml` 에 `topology` 는 있고
   `branch` 는 없으며, 브랜치≠토폴로지 게이트(`branch_verified`)는 테라포밍 1회 attestation 이라 캠페인 진입에서
   재검사하는 실행자가 0 이다. 9-11 사고에서 울린 유일한 트립와이어는 사람이었다(§5·§6).

## 4. `sync_branches.sh` 의 정체

- **자기 선언**(헤더): "공유 빌딩블럭을 정본(main) → multi-node 로 복사 · 커밋은 사람이". 기본
  `SRC_BRANCH=main`(부재) · `DST_BRANCH=multi-node`. 즉 설계는 **정본 하나 + 미러 하나**였고, 실무의
  양방향은 env override 로 생긴 관행이다.
- **메커니즘**: 목적지 체크아웃에서 `git checkout <SRC> -- <allowlist>` + MIRROR_DIRS 의 목적지-only 파일
  `git rm` 스테이징. 머지가 아니라 **덮어쓰기**다. 그래서 (a) 미커밋 워킹트리 편집을 무경고 파괴
  (`audit_26090115` §⑥ · dirty 검사 0), (b) 목적지에만 있는 더 새로운 변경을 소실 → cherry-pick 선행 절차가
  생김(`devlog_26090718`), (c) 하네스 세대가 바뀐 첫 sync 에서 자기 배달물에 막힘(9-03 부트스트랩).
- **allowlist**(정본 그대로): `CLAUDE.md` · `.claude/{rules,skills,schemas,policies,hooks}` · `.gitignore` ·
  `manifest.template.yaml` · `.gitattributes` · `HINTS.md` · `README.md` · `hints` · `assets` · `campaigns` +
  트리 열거 `docs/report/*`·`docs/*/example.md`·(2026-09-10 철회 전) `docs/benchmark/benchmark_*.yaml`.
- **제외**: `output/<t>/**` 빌드킷·build_patches* · 실값(`manifest.yaml`·`config.yaml`·`*.local.json`) · `seed/` ·
  작업 문서(`docs/{plan,devlog,testlog,_evidence}`) · **multi 의 손작성 compose/serve 구현**.
- **관찰**: allowlist 는 "빌딩블럭 = 추적·배포 대상" 헌법 문장을 그대로 옮긴 것이라, 사실상 **토폴로지 고유가
  아닌 모든 것**이 매번 복제된다. 한 파일이 두 브랜치에 두 번 존재하고 git 이 두 자리를 든다 —
  `policy:GIT_SINGLE_AUTHORITY` 2문항이 잡으려던 "같은 사실 두 자리"가 브랜치 단위로 재현된다.
- **추적 증거가 브랜치에 갇힌 사례**: 인증서를 추적하자 multi 에서 커밋한 2건이 single 체크아웃에서 사라져
  `EVIDENCE_MISSING`(`devlog_26091021`) → 추적 예외 철회. report·hint 카탈로그는 같은 성질인데 아직 추적이다(§2.1).

## 7. 딥 인터뷰에 올릴 숨은 가정과 결정 축

아래는 답이 아니라 **답해야 결정이 성립하는 질문**이다. 각 축의 현재값은 §1~§6 의 실측이다.

1. **브랜치의 정체는 무엇인가** — ① 산출물 통로 토글(코드가 집행 중) ② 독립 배포 라인(헌법 선언) ③ 작업
   성격·서브 자율성 모드 선언(사용자 기대 · 집행자 0). 셋을 한 ref 가 계속 겸할 것인가, 갈라 놓을 것인가.
   현재값: 셋이 한 ref 에 겹쳐 있고 ③만 집행되지 않는다.
2. **공유 빌딩블럭의 단일 소유** — 정본 브랜치를 고정할 것인가(어느 쪽?), 공유 빌딩블럭을 **세 번째 자리**
   (별도 브랜치·서브모듈·디렉터리)로 빼고 두 토폴로지 브랜치는 델타만 들 것인가, 아니면 덮어쓰기 대신
   **git merge/rebase 계열**(공통 조상 유지)로 갈 것인가. 현재값: 정본이 두 번 뒤집혔고 머지 0 · 배타 커밋 343/263.
3. **동기화의 방향·트리거·범위** — 단방향 고정인가, 역방향 허용 조건은 무엇인가(현재 후속 미해소),
   사람 질의 유지인가 커밋 훅인가, allowlist 를 "토폴로지 고유가 아닌 전부"에서 좁힐 것인가.
4. **노드별 특화 동작의 실체** — 사용자가 원하는 "노드별 특화"는 무엇이 달라지는 것인가: 활성 스킬 집합·
   러너·가드·서브 정체·기본값. 현재 `node_role_contract` 가 tool_plane 차등(3 vs ∅)을 **manifest 토폴로지에서**
   이미 파생한다. 브랜치가 이것을 다시 결정해야 하는가, 아니면 브랜치는 통로만 남기고 특화는 manifest 가
   전담하는가.
5. **브랜치≠토폴로지 게이트의 실행자** — `branch_verified` 는 테라포밍 1회다. 캠페인 init·서빙 기동·벤치 진입에서
   누가 다시 검사하는가. 검사 실패 시 행동은 차단인가 안내인가(헌법 노드제어 ③ "처방을 누가 실행하는가").
6. **브랜치 파생 코드 13곳의 처분** — 헌법대로 manifest/선언 권위로 바꿀 것인가(그러면 통로 선택기 역할도
   manifest 로 옮겨야 한다), 헌법을 현실("브랜치 = 통로 선택기")로 고칠 것인가. unknown→single 기본값의 처분.
7. **append-only 산출물의 거처** — `docs/report`·hint 카탈로그·(철회된) 인증서처럼 토폴로지 무관인데 브랜치에
   갇히는 것들을 어디에 둘 것인가. 현재값: report 31 vs 33 · 카탈로그 +109줄 편차.
8. **서브 노드의 브랜치** — 서브 로컬 git 도 single/multi 두 브랜치를 갖고 `sync_to_sub --branch` 가 그리로
   `[sync]` 커밋한다. 메인 설계가 바뀌면 서브 렌더 트리·배달 평면 계약(§2.7.0)이 따라 바뀐다 — 그 순서.
9. **히스토리의 처분** — 영원히 갈라진 두 그래프를 그대로 둘 것인가, 한 번 합류시킬 것인가(합류는
   hint 태그 앵커·`hint_branch.py` 의 `git branch --contains` 판정에 영향).
10. **전환 비용 vs 모드 신호** — 74회/9일 전환과 "서빙 중 전환 금지" 함정을 `git worktree` 동시 체크아웃으로
    없앨 수 있으나, 그러면 "현재 브랜치 = 현재 모드"라는 신호 자체가 사라진다. 어느 쪽을 택하는가.
