## TP=1 vs TP=2 — 무엇이 왜 다른가

GPU 1장(TP=1)에서 2장 전부(TP=2)로 바꾸면 세 가지가 **서로 다른 배율**로 바뀐다 — "TP=2 는
다 2배"가 아니다:

| 축 | TP=1→TP=2 배율 | 원인(추정, 정량 미검증) |
|---|---|---|
| 단일스트림 decode 속도 | ~1.58배(fp8w) · ~1.75배(bf16w) | TP 연산 분산 효과 − 통신(all-reduce) 오버헤드 |
| 동시접속 한계(batch) | ~2.67배(fp8w+fp8kv 조합 기준, 6→16) | 가중치가 카드당 절반이 되고 KV 도 TP 로 샤딩되는 효과가 겹침 |
| 최대집계 처리량 | ~2.12배(1181.6→2503.2) | 위 두 배율의 합성 효과 |

가중치양자화(fp8 vs bf16)에 따라서도 속도 배율이 다르다(fp8w 1.58배 vs bf16w 1.75배) —
가설은 절대 VRAM 감소폭 차이(bf16 은 51.1→25.55GiB/카드, fp8 은 28.22→14.11GiB/카드)지만
검증되지 않았다.

## 환경 특이사항 (재현 시 필독)

이 두 캠페인 모두 **Docker를 쓰지 않는 환경**(비특권 컨테이너 — Docker-in-Docker 구조적 불가)
에서 수행됐다. 대체 경로(venv 직접설치+네이티브 프로세스+GuideLLM pip)는 TP=1 리포트와 동일 —
반복하지 않는다.

**TP=2 캠페인 착수 전 발견한 코드 gap**: 레시피 생성기(`gen_recipe_set.py`)는 배포 3종
세트(yaml)에 `tensor-parallel-size` 를 정확히 반영했지만, Phase 2 트라이얼 실행 경로
(`run_trial.py`)는 그 값을 전혀 소비하지 않아 TP>1 을 요청해도 트라이얼이 조용히 TP=1 로
로드되고 있었다(TP=1 캠페인만 돌던 동안은 드러나지 않았다). `--tensor-parallel-size`
이미터를 추가해 교정 — 이 프로젝트를 그대로 쓰는 재현자는 이미 반영된 코드를 받는다.

## 핵심 인사이트

1. **KV 양자화가 두 캠페인 모두에서 동시접속 처리량의 지배 변수다** — 다만 그 한계효용은
   TP 에 따라 다르다. TP=1 에서는 A→B 로 KV 를 양자화하면 집계처리량이 9배(131.0→1181.6)
   뛰었지만, TP=2 에서는 E→F 로 같은 전환이 1.27배(1965.7→2503.2)에 그쳤다 — TP=2 가 이미
   각 조합에서 상당한 여유 예산을 갖고 있어 KV 양자화의 상대적 이득이 좁혀진 것으로 추정
   (검증 필요한 후속 가설).
2. **가중치 양자화는 단일스트림 속도를 지배하며, 이 관계는 TP 와 무관하게 일관된다** — TP=1:
   fp8 43.9~44.3 vs bf16 26.8(~1.6배 차) · TP=2: fp8 69.6~69.8 vs bf16 46.9(~1.5배 차).
3. **컨텍스트 상한은 짧은 입출력 측정(1024/256 토큰)에서 decode 속도에 거의 영향 없다** — 이
   패턴이 두 캠페인 4쌍(A/D, E/H 등)에서 반복 확인됐다. 다만 이는 "실제로 쓰는 컨텍스트가
   짧을 때"의 결론이다 — 긴 프롬프트/누적 멀티턴에서는 다를 수 있다(미검증 영역).
4. **"물리적으로 불가"라는 결론은 실측 없이는 신뢰할 수 없다** — TP=1 캠페인은 예산 계산만
   으로 YaRN 1M 을 포기했으나, TP=2 실측은 그 결론을 뒤집었다(자매 셀 H). 여유 예산이 있을 때는
   추정에 머물지 말고 실제 트라이얼로 확인하는 편이 안전하다.
5. **얕은 부하 스윕은 "최대동시 처리량" 질문에 답하지 못한다** — TP=2 캠페인 1차 시도가
   `--levels 1,2,3` 으로 각 셀의 실제 batch 상한(8~16)에 크게 못 미치게 측정했다가 재측정한
   사례(testlog 참조) — 스윕 레벨은 각 셀의 실제 batch 상한까지 닿아야 한다.

  영향 없음. 미수정 후속과제로 남아 있다.
- **TP>1 판정의 추가 낙관 편향**: `roofline.py` 는 TP>1 인데 interconnect 대역폭이 미상이면
  통신 비용을 0으로 취급한다(TP=2 4셀 floor=19.19 는 이 낙관 가정 위에 서 있다) — 4셀 모두
  ratio>2 로 여유 있게 PASS 했으나, 더 타이트한 마진의 조합에서는 이 편향이 오판을 만들 수
  있다. 후속과제.
- TP=1→TP=2 세 배율(속도 1.58~1.75배·batch 2.67배·집계 2.12배)의 정확한 원인 분해(TP 통신
  오버헤드 vs 가중치 샤딩 효과)는 이 벤치의 측정 범위 밖 — NCCL/all-reduce 프로파일링이 필요한
  별도 질문.
- `lite_bench.sh` 는 아직 docker 전용 — native 모드 미패치(두 캠페인 공유).
