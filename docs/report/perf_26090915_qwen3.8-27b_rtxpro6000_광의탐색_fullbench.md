## 환경 특이사항 (재현 시 필독)

이 캠페인은 **Docker를 쓰지 않는 환경**(비특권 컨테이너 — Docker-in-Docker 구조적 불가)에서 수행됐다.
이 프로젝트의 표준 산출물(NGC 베이스 컨테이너·`docker compose` 서빙)은 Docker 를 전제하므로, 이번
캠페인 한정으로 다음과 같이 대체했다:
- 컨테이너 빌드 대신 vLLM 0.28.0 + torch 2.13.0(+cu129)을 프로젝트 전용 `.venv` 에 벤더 wheel로 직접 설치.
- 서빙은 `docker compose up` 대신 `vllm serve` 를 이 호스트의 네이티브 프로세스로 직접 기동
  (GPU 격리는 `CUDA_VISIBLE_DEVICES` 로 수행).
- 측정 도구(GuideLLM)도 별도 컨테이너 대신 pip 패키지로 직접 설치·실행.
- Docker 환경에서 재현할 때는 이 대체가 불필요하며, 표준 3종 세트(`output/single/configs/*.{yaml,sh}`,
  `envs/.env.*`)를 그대로 `docker compose` 로 띄우면 된다(단, 아래 KV 절대클램프·batch·양자화 값은
  이 GPU 예산 기준 실측이므로 동일 GPU/동일 TP 에서만 그대로 유효하다 — 다른 GPU 면 재측정 권장).

## 핵심 인사이트

1. **KV 양자화가 이 하드웨어에서 동시접속 처리량의 지배 변수다.** 가중치양자화가 같은 A/B 비교에서
   단일 스트림 속도는 거의 동일(43.91 vs 44.22)하지만, KV를 fp8로 줄인 B만 batch=6까지 늘릴 수 있어
   집계 처리량이 **9배** 차이난다. "최대 context + 남은 KV로 동시접속 유지" 전략에서 KV 양자화가
   최우선 레버다.
2. **가중치 양자화(fp8 vs bf16)는 단일 스트림 속도에 ~1.6배 영향**(43.9 vs 26.8) — 메모리 대역폭
   결정 레짐에서 예상된 방향이다. 정확도가 더 중요해 bf16 이 필요한 경우, 처리량 저하를 감수하는
   대안으로 유효(셀 C도 PASS).
3. **네이티브 262144 컨텍스트가 이 GPU 1장 예산의 실질 상한**이다. YaRN 확장(524288/1M)은 fp8가중치+
   fp8KV 최선 조합으로도 이 GPU 1장(96GB)엔 들어가지 않는다(524288: 69.6GB 추정 — 안전마진 통과했지만
   실측 전 보류; 1M: 모든 조합에서 물리 예산 초과, GPU 2장 이상 필요).

  루프라인(물리 상한 기반 기댓값) 단독 판정**으로 통일했다(더 보수적인 기준, 결론(PASS)에는 영향
  없음). 상세: `docs/testlog/testlog_26090915_Qwen3.8.27B_광의탐색_3셀_FullBench_비교.md`.
- 초기 판정에는 이 GPU 1장만 쓰는데도 tensor_parallel_size=2 로 잘못 표시되는 결함이 있었다(레시피
  생성기가 "TP=1은 vLLM 기본값이라 안 적는다"는 설계를 따랐는데, 노드 GPU 일부만 쓰는 이번 경우엔
  그 전제가 깨졌다). 레시피 yaml에 `tensor-parallel-size: 1` 을 명시해 정정, 재측정 없이 기존
  실측으로 재판정했다 — 판정(PASS) 불변.
- YaRN(524288/1M) 컨텍스트 확장은 이 프로젝트의 서빙 트리플릿 생성기가 `--hf-overrides` 를 아직 지원하지
  않아 자동 생성 경로에서 보류했다. 필요 시 별도 런타임 패치 작업으로 가능(수동 검증 선례는
  `docs/report/perf_26082421_qwen3.8-27b_레시피별_성능.md` 참조 — 단 그 문서는 다른 하드웨어(DGX Spark
  GB10) 기준이라 절대 수치는 이 리포트와 직접 비교 불가).
