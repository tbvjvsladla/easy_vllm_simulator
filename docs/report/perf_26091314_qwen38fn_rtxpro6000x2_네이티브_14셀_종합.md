## 1. 환경 특이사항 (재현 시 필독)

Docker-in-Docker 가 구조적으로 불가한 호스트(비특권 컨테이너 · systemd offline)에서 수행했다.
컨테이너 빌드 대신 **vLLM/GuideLLM 을 프로젝트 venv 에 직접 설치하고 `vllm serve` 를 호스트
프로세스로 기동**했다(GPU 격리는 `CUDA_VISIBLE_DEVICES`). 이 대체 경로는 이번에 **저장소 코드로
편입**됐다 — 기동·teardown·예산갱신·워치독·벤치가 `--plane native` 로 분기한다.

> ⚠ 선례 리포트(`perf_26090918`)는 같은 칩의 **Server Edition** 이다. 이 노드는 **Max-Q**(저전력
> 워크스테이션판)라 클럭·TDP 가 낮다. 선례 수치를 이 표의 기대치로 쓰지 말 것.

## 2. 엔진 핀은 성능 선택이 아니라 **구동 가능성의 전제**다

vLLM **0.29.0 정식으로는 NVFP4 체크포인트를 서빙할 수 없다.** 가중치 로딩에서 즉사한다:

```
ValueError: There is no module or parameter named 'ngram_embedding.weight_scale'
            in Qwen4ExpNGramEmbedding
```

0.29.0 의 PLE quant method 선택이 `Fp8Config` 전용이라 NVFP4 는 unquantized 경로로 가는데,
그 경로에는 체크포인트가 들고 있는 `weight_scale` 을 받을 파라미터가 없다.
nightly(main)에는 `ModelOptMixedPrecisionConfig` 와 `Qwen4ExpPLEPinnedHostEmbedding` 이 들어와
있어 NVFP4 PLE 양자화와 PLE CPU 오프로드가 **둘 다 정식 기능**이다.

- PLE 오프로드 노브: `--engram-config '{"cpu_offload":true}'` (레거시 `VLLM_PLE_CPU_OFFLOAD=1`)
- 0.29.0 에는 `vllm.config.engram` 모듈 자체가 없다(설치본 실측).

## 3. KV 양자화 축은 이 아치에서 열리지 않는다

```
Qwen4ExpQSAFlashAttentionBackend.supported_kv_cache_dtypes = ['auto', 'bfloat16']
```

같은 파일의 일반 FlashAttention 백엔드는 `fp8`·`fp8_e4m3` 를 받는데 **이 아치 전용 백엔드만**
막혀 있다(설치본 런타임 실측). 따라서 `kv_cache_dtype` 는 축이 아니라 상수다.

## 4.5 Full bench — 동시성 곡선 (2026-09-13 추가 수행)

§4 의 lite 측정은 전 셀 **동시성 1** 이었다. 최고 성능 셀(FP8 · offload · 512K)에 대해
정규 경로(`sweep_bench` → `judge_bench` → `render_report`)로 full bench 를 추가 수행했다.

측정: GuideLLM 0.7.3(호스트 venv) · 레벨당 32요청 + warmup 4 · 입력 1024 · 출력 256 ·
`--backend openai` · 절삭 0건.

| 동시성 | 출력 t/s | 집계 t/s | TTFT | 완주/실패 |
|---:|---:|---:|---:|---|
| 1 | 12.45 | 62.3 | 121 ms | 32 / 0 |
| 2 | 24.14 | 120.8 | 279 ms | 32 / 0 |
| 4 | 47.51 | 237.7 | 374 ms | 32 / 0 |
| **8** | **78.94** | **395.0** | 626 ms | 36 / 0 |

**동시성 8 까지 6.3배로 거의 선형이다.** 단일스트림만 보면 이 구성은 느려 보이지만,
배치에서는 값을 한다 — §4 의 lite 표만으로는 보이지 않던 축이다.

### 판정 — `REFUTE`, 그리고 그것이 뜻하는 것

```
루프라인 기대 achievable   19.49 t/s   (R_fp/R_token 55.69 · MBU 반영)
단일스트림 실측            11.93 t/s   ratio 0.612
failure_axis: meet · structural_or_strategy: strategy
authority: explore
```

`authority=explore` 는 **문턱을 세우지 않는다**(광의탐색이라 성능·밸런스 축 모두 서술).
승격 자격은 성능 판정이 아니라 **서빙 성립 + 유효 측정**이며 둘 다 충족했다.
인증서는 PASS 때만 발행되므로 나오지 않았고, 이 런은 `bench_report` 로 증거를 바인딩했다.

**판정을 오독하지 말 것**: 이 REFUTE 는 **MTP off 조건**에서 났다. 같은 셀에 MTP k=3 을 켜면
lite 기준 **29.37 t/s** 로 루프라인 기대치를 넘는다. 즉 "이 하드웨어가 느리다"가 아니라
"MTP 없이는 메모리대역 상한의 61% 만 쓴다"가 정확한 독해다.

## 5. 축별로 무엇이 드러났나

### 5.1 MTP 가 지배적 레버다 — 그리고 "1/3 성능"은 측정조건 불일치였다

MTP(`--speculative-config '{"method":"qwen4_exp_mtp","num_speculative_tokens":3}'`)는
전 셀에서 **2.13~2.33배**를 준다. 엔진 실측 acceptance length 2.63~3.47.

커뮤니티 기준선(다른 하드웨어, 33 t/s)은 **MTP k=3 · acceptance 2.78 조건**이다. 기저로 환산하면
`33.0 / 2.78 ≈ 11.9 t/s` 로 우리 기저(11.7~12.7, MTP 없음)와 같은 범위다. MTP 를 켜지 않고
비교하면 "1/3 성능"으로 보이지만 **측정조건이 다른 것**이다.

### 5.2 PLE offload vs device — 컨텍스트와 상호작용하고, 변종마다 방향이 다르다

```
NVFP4   262k  off 12.653 / dev 12.716   차이 없음
        512k  off 11.677 / dev 12.743   dev +9.1%
        1M    off 11.775 / dev 12.690   dev +7.8%
FP8     262k  off 12.201 / dev 12.559   dev +2.9%
        512k  off 12.718 / dev ❌        (dev 는 VRAM 불가)
```

NVFP4 는 확장 컨텍스트에서 offload 가 ~8% 비용을 물고, FP8 은 offload 로 262k→512k 가
**오히려 +4.2%** 올랐다. 방향이 반대이므로 단일 기전으로 설명되지 않는다 — **미규명**이다.

실용 지침: **VRAM 이 허락하면 device(상주), 부족하면 offload**. FP8 로 512K 이상을 쓰려면
offload 가 선택이 아니라 필수다.

### 5.3 컨텍스트 확장의 비용은 한 번만 치른다

NVFP4 offload 기준 `262k 12.653 → 512k 11.677(-7.7%) → 1M 11.775(+0.8%)`.
YaRN factor 2→4 는 추가 비용이 사실상 없다. **512K 를 쓸 바엔 1M 을 쓰는 편이 낫다.**

### 5.4 가중치 총량보다 active 경로가 지배한다

FP8 체크포인트는 NVFP4 의 **1.40배**(176,928 vs 126,533 MiB)인데 디코드 손실은 262k 에서
**3.6%** 에 그친다. MoE 라 active 파라미터(6B)가 같아 메모리대역 병목이 비슷한 것과 정합한다.

### 5.5 TP=2 는 이기지만, PCIe 가 병렬 이득의 대부분을 먹는다

TP=1 대조(NVFP4·offload·262k): `11.688 t/s` vs TP=2 `12.653` → **+8.3%**.
TTFT 는 212 → 117 ms(−45%)로 프리필에서 TP=2 가 확실히 이긴다.
다만 같은 GPU 계열 dense 27B 선례의 TP1→TP2 배율이 1.58~1.75배였던 것에 비하면 **1.08배**로,
NVLink 부재(PCIe P2P)의 대가가 크다.

## 6. VRAM 예산 — 결정론 추정과 실측

per-GPU 97,887 MiB · TP=2 · `enforce-eager`.

| 구성 | weights/GPU | 실측 총 VRAM | 분해 |
|---|---:|---:|---|
| NVFP4 offload | 38,852 | 60,360 | + KV 16,384 + 활성화 5,124 |
| NVFP4 device | 63,266 | 84,690 | + KV 16,384 + 활성화 ~5,040 |
| FP8 offload | 64,050 | 84,682 | + KV 16,384 + 활성화 ~4,248 |
| FP8 device | 88,464 | **96,678 (98.8%)** | + KV 4,096 + 활성화 4,118 |

결정론 추정과 실측이 **전 구성에서 1 MiB 내**로 맞았다.

### KV 공식 정정 — 하이브리드 아치의 함정

`full_attention` 층만으로 KV/token 을 계산하면 **약 12% 과소산정**된다.
`linear_attention` 36층의 상태(conv/ssm)가 **같은 KV 풀에서 잡히기** 때문이다.

```
내 공식(full-attn 12층만)  262,144 → 3,072 MiB
엔진 실제 요구                      → 3,451 MiB    계수 1.1233
```

이 계수를 512K·1M 에 적용한 예측과 엔진 요구가 **0.14% 오차**로 일치했다(6.74 vs 6.73 GiB,
13.48 vs 13.46 GiB). KV 클램프에 여유가 있을 때는 드러나지 않고, 여유가 얇은 구성에서만
터진다 — FP8 device 가 그 경우였다.

## 7. 재현성

셀별로 표준조건 3회를 돌려 **자체 산포**를 냈다. 산포는 **셀 간 이식되지 않는다**:
한 셀에서 0.34~0.74%, 다른 셀에서 5.74~5.96% 로 10배 차이가 난다. 따라서 단일 측정으로
셀 간 차이를 판정하지 않았고, 밴드 밖일 때만 축 효과로 읽었다.

## 8. 한계와 미규명

- **미규명**: §5.2 의 변종별 방향 반전. 커널 선택·양자화 경로 차이가 후보이나 검증하지 않았다.
- 동시성 축은 **최고 성능 셀 1개에 대해서만** 측정했다(§4.5). 나머지 9개 measured 셀은
  여전히 동시성 1 단일스트림이며, 그 셀들의 배치 특성은 이 리포트가 말하지 않는다.
- 정확도 평가(gsm8k·aime 등)는 수행하지 않았다. 속도·용량 지도일 뿐이다.
- 큰 산포(5.7~6.0%)가 간헐적으로 나타나는 원인을 규명하지 않았다.
- Max-Q 판이므로 Server Edition 수치와 직접 비교할 수 없다.
