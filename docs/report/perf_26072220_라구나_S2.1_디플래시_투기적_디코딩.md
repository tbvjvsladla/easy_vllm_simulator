# Laguna S 2.1 — DFlash 추측 디코딩(Speculative Decoding) 유/무 성능 비교

**대상**: `poolside/Laguna-S-2.1-NVFP4` (117.6B total / 8.5B activated MoE)
**하드웨어**: NVIDIA GB10 (통합메모리 · sm_121a · aarch64) 1장/노드, 2노드 각각 독립 서빙
**소프트웨어**: vLLM 0.25.1 (source-build) · CUDA 13.2 · 이미지 `easy-vllm:0.25.1-cu132-aarch64-source`
**측정일**: 2026-07-22

---

## 1. 한 줄 요약

> **같은 GB10 한 장에서, DFlash 추측 디코딩은 실제 코딩 프롬프트 기준 토큰 생성 속도를 약 2.1배 올린다.
> 단, 이 이득은 동시 요청이 늘면 사라지고 첫 응답까지의 지연(TTFT)은 오히려 약 2배 나빠진다.**

| | 추측 디코딩 없음 | DFlash 있음 | 배수 |
|---|---|---|---|
| 실제 코딩 프롬프트 생성속도 | 19.6 tok/s | **41.6 tok/s** | **2.13×** |
| 합성 벤치 생성속도 (동시성 1) | 19.5 tok/s | 28.7 tok/s | 1.47× |
| 총 처리량 (동시성 8) | 83.4 tok/s | 79.4 tok/s | **0.95×** |
| 첫 토큰 지연 TTFT p50 (동시성 1) | **147 ms** | 296 ms | 2.01× (나쁨) |

---

## 2. 무엇을 어떻게 측정했나

두 노드에 **완전히 동일한 서빙 설정**으로 같은 모델을 올리고, **추측 디코딩 켬/끔만을 유일한 변수**로 두었다.

- **A 노드 (대조군)** — Laguna-S-2.1-NVFP4, 추측 디코딩 **없음**
- **B 노드 (실험군)** — 동일 모델 + `Laguna-S-2.1-DFlash-NVFP4` 초안(draft) 모델, `num_speculative_tokens=15`

### 변수 통제 감사 결과

비교의 타당성을 담보하기 위해 두 노드의 실제 기동 인자를 기계적으로 대조했다.

| 축 | 결과 |
|---|---|
| 서빙 설정 파일 10개 항목 | **전건 일치** |
| `vllm serve` CLI 플래그 | **차이 = `--speculative-config` 단 1개** |
| 런타임 환경변수 | 전건 일치 |
| 이름 3종(컨테이너·프로젝트·설정파일명) | 의도적으로만 상이 |

> **KV 캐시 용량은 의도적으로 다르다.** 절대 클램프(16 GiB)는 동일하게 걸었지만, 추측 디코딩 노드는 그 예산
> 안에서 초안 모델의 KV까지 함께 부담한다. 결과적으로 사용 가능한 컨텍스트 토큰 수는
> **679,022 → 457,049** 로 줄어든다(동일 컨텍스트 기준 동시 처리 여력 2.59× → 1.74×).
> "**같은 메모리 예산에서 추측 디코딩이 이득인가**" 가 더 정직한 질문이라 보고 이 상태를 그대로 두었다.

## 3. 서빙 전략 (양 노드 공통)

```
tensor-parallel-size      1
max-model-len             262144      # 모델카드가 권장하는 품질 인증 설정
gpu-memory-utilization    0.85        # 통합메모리 상한 0.90 준수
max-num-seqs              32          # DFlash 는 기본값 256 에서 vLLM 을 크래시시킴
kv-cache-dtype            auto        # → FP8(e4m3) 자동 선택
kv-cache-memory-bytes     17179869184 # 16 GiB 절대 클램프 (실측 기반 산정)
reasoning-parser          poolside_v1
tool-call-parser          poolside_v1 + --enable-auto-tool-choice
--override-generation-config    {"temperature":0.7,"top_p":0.95}
--default-chat-template-kwargs  {"enable_thinking":true}
```

**B 노드에만 추가되는 유일한 인자**

```
--speculative-config '{"model":"<DFlash 체크포인트 경로>","num_speculative_tokens":15,"method":"dflash"}'
```

MoE 백엔드는 **지정하지 않았다** — 자동 선택이 `FLASHINFER_CUTLASS` 를 고르며 이것이 sm_121 네이티브 경로다.

## 4. 결과 ① — 부하 스윕 (동시 요청 수를 늘리며)

합성 벤치(`vllm bench serve`, 입력 1024 토큰 / 출력 256 토큰 / 요청 16건)로 동시성을 1→8로 올리며 측정했다.

### 요청 하나가 체감하는 생성 속도

| 동시성 | 추측 없음 | DFlash | 배수 |
|---:|---:|---:|---:|
| 1 | 19.50 tok/s | 28.69 tok/s | 1.47× |
| 2 | 17.71 tok/s | 18.18 tok/s | 1.03× |
| 4 | 14.08 tok/s | 15.27 tok/s | 1.08× |
| 8 | 10.53 tok/s | 12.14 tok/s | 1.15× |

### 서버 전체가 뽑아내는 총 처리량

| 동시성 | 추측 없음 | DFlash | 배수 |
|---:|---:|---:|---:|
| 1 | 19.28 tok/s | 26.86 tok/s | 1.39× |
| 2 | 34.90 tok/s | 34.43 tok/s | 0.99× |
| 4 | 55.65 tok/s | 57.03 tok/s | 1.02× |
| 8 | 83.42 tok/s | 79.36 tok/s | **0.95×** |

### 첫 토큰까지의 지연 (TTFT p50)

| 동시성 | 추측 없음 | DFlash | 차이 |
|---:|---:|---:|---:|
| 1 | 147 ms | 296 ms | +101% |
| 2 | 250 ms | 474 ms | +90% |
| 4 | 290 ms | 598 ms | +106% |
| 8 | 332 ms | 714 ms | +115% |

**해석** — 추측 디코딩은 *연산을 써서 지연을 줄이는* 기법이다. 동시 요청이 차면 GPU가 이미 포화라
바꿔줄 여유가 없어져 **총 처리량 이득이 사라진다**. 반면 초안 모델을 매 스텝 돌리는 비용은 그대로 남아
**TTFT는 어느 부하에서도 약 2배 나쁘다**.

## 5. 결과 ② — 실제 프롬프트로 재측정 (중요)

합성 벤치의 수치를 그대로 믿으면 **추측 디코딩을 과소평가하게 된다.**

표준 벤치는 **무작위 합성 토큰**을 생성하고 샘플링 온도도 0.7이다. 초안 모델은 무작위 토큰을 맞출 수 없으므로
수용률이 인위적으로 낮아진다. 모델 제작사가 공개한 수치는 실제 데이터셋(GSM8K·HumanEval·MBPP·MT-Bench) +
`temperature=0` 기준이다.

동일 조건을 맞춰 **실제 코딩 프롬프트 + greedy(temperature 0)** 로 3회 반복 측정했다.

| 반복 | 추측 없음 | DFlash | 수용 길이 | 배수 |
|---:|---:|---:|---:|---:|
| 1 | 19.50 tok/s | 40.73 tok/s | 5.13 | 2.09× |
| 2 | 19.64 tok/s | 40.76 tok/s | 5.11 | 2.08× |
| 3 | 19.58 tok/s | 43.43 tok/s | 5.47 | 2.22× |
| **평균** | **19.57 tok/s** (±0.4%) | **41.64 tok/s** (±3.3%) | 5.24 | **2.13×** (±3%) |

수용 길이 5.1~5.5는 모델카드가 보고한 범위(4.2~6.4)와 일치한다.

> **이 해석의 결정적 증거**: 대조군이 두 조건에서 **똑같이 19.5 tok/s** 를 냈다. 추측 디코딩이 없는 쪽은
> 메모리 대역폭에 묶여 있어 어떤 데이터를 넣든 속도가 같고, 따라서 두 측정의 차이는 **전적으로 초안 모델의
> 수용률에서** 온다는 것이 통제군으로 증명된다.

**재현성도 역전된다.** 합성 벤치의 추측 디코딩 측정은 런마다 ±20%까지 흔들렸지만(동시성 1에서 24.3 / 27.6 /
28.7 tok/s), 실제 프롬프트 + greedy 측정은 ±3%로 안정적이다. 확률적 샘플링이 수용률을 흔들기 때문이다.

⚠️ **추측 디코딩을 쓰는 모델을 벤치할 때는 반드시 실제 텍스트 + greedy 조건으로도 측정하라.**

## 6. 결론 — 어떤 구성을 쓸 것인가

| 사용 형태 | 권고 | 이유 |
|---|---|---|
| **1인 코딩 어시스턴트 / 대화형 에이전트** | **DFlash 켬** | 체감 생성속도 2.1배. TTFT 150ms 증가는 사람이 거의 못 느낌 |
| **팀 공용 · 다중 세션 동시 서빙** | **DFlash 끔** | 총 처리량 이득 없음(동시성 8에서 오히려 0.95×) + TTFT 2배 악화 + 컨텍스트 여력 감소 |
| **긴 컨텍스트가 최우선** | **DFlash 끔** | 같은 메모리 예산에서 사용 가능 토큰이 679K → 457K 로 감소 |

## 7. 참고 — 판정 근거

두 구성 모두 결정론 성능 게이트를 통과했다. 기준값은 모델 제작사가 **동일 하드웨어(DGX Spark GB10)** 에서
보고한 실측치다.

| | 추측 없음 | DFlash |
|---|---|---|
| 측정값 (동시성 1) | 19.50 tok/s | 28.69 tok/s |
| 기준(레퍼런스) | 13 tok/s | 15 tok/s |
| 합격선 (기준 × 0.85) | 11.05 tok/s | 12.75 tok/s |
| 기준 대비 | **1.50×** | **1.91×** |
| 판정 | **PASS** | **PASS** |

이론 상한(메모리 대역폭 273 GB/s · 활성 가중치 9.8 GiB 기준 100% 활용 가정)은 25.94 tok/s이며,
대조군의 실효 대역폭 활용률은 약 75%다. 추측 디코딩 노드는 이 상한을 넘을 수 있는데, 한 번의 forward pass로
여러 토큰을 확정하기 때문이다(수용 길이 배수만큼 상한이 올라간다).

## 8. 재현 시 주의사항

- **이 수치는 위 환경 한정이다.** 다른 하드웨어·드라이버·이미지·컨텍스트 길이에서 그대로 성립하지 않는다.
  소비 전 재측정할 것.
- **KV 절대 클램프 값(16 GiB)을 복사하지 말 것.** 통합메모리 용량에 따라 달라진다. 언클램프로 1회 기동해
  서빙 로그의 KV 캐시 크기로 토큰당 바이트를 실측한 뒤 역산하는 것이 안전하다.
- **`MAX_JOBS` 를 반드시 제한할 것.** 통합메모리 장비에서 커널 JIT 컴파일이 무제한으로 병렬화되면 메모리를
  고갈시켜 **호스트 전체가 내려갈 수 있다**(모델카드 경고). 본 측정 환경에서는 2로 확정했으며, 이 값은
  장비마다 재확인이 필요하다.
- **컨테이너로 서빙한다면 JIT 캐시를 호스트에 영속화하라.** 컨테이너를 다시 만들 때마다 컴파일 캐시가
  사라져 매번 cold JIT이 되고, 위 위험을 매 기동마다 다시 지게 된다. 캐시를 마운트하면 워밍업이
  732초 → 1.23초로 줄어든다.
- **추론(reasoning) 분리가 안 되면** 서버에 `--default-chat-template-kwargs '{"enable_thinking":true}'` 를
  지정했는지 확인하라. 이 설정이 없으면 파서가 조용히 비활성 모드로 떨어져 `</think>` 가 응답 본문에 섞인다.
- **`min_p` 를 기본 생성 설정에 넣지 말 것.** 추측 디코딩 사용 시 vLLM이 거부해 모든 요청이 400으로 실패한다.
